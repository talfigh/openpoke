# Working notes

Running list of problems found while setting up and running OpenPoke. These feed the README's "Other gaps" section. Each entry says where it was found and its status.

Status key: **fixed** (committed on `agent-overload`), **pending** (known fix, not applied yet), **open** (needs design or is out of scope), **won't fix** (deliberately left as upstream).

## 6. Offline baseline on synthetic data (2026-10-27)

The fake Gmail backend (`server/services/gmail/fake_backend.py`, enabled by `OPENPOKE_FAKE_GMAIL`) answers every Composio call from `evals/fixtures/synthetic/mailbox.json` (995 emails, distinct senders, fixes 5.1 and 5.2) and records writes to an outbox file. Nothing is sent. `OPENPOKE_DATA_DIR` isolates each run. Harness: `evals/run_baseline.py`; runs in `evals/baseline/runs/`. All roles on `anthropic/claude-haiku-5.5`.

**Routing sweep** (`2026-10-27_105605_routing_baseline`, first of 3 runs, means in 7.1; 131 labeled prompts × roster sizes, Interaction Agent loop with dispatch stubbed, $1.36 total):

| ------ | -------- | ---------- | ------------------ | ---------------------------------- | ------------- | --------- |
| 40     | 73%      | 74%        | 24%                | 31%                                | 5.8k          | 86%       |
| 100    | 75%      | 74%        | 24%                | 28%                                | 7.2k          | 86%       |
| 250    | 71%      | 68%        | 26%                | 31%                                | 10.5k         | 86%       |
| 500    | 59%      | 58%        | 39%                | 34%                                | 16.1k         | 14%       |

| #   | Finding                                                                                                                                                                                                                                                                              |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 6.1 | **Overload is real past ~250 agents.** Reuse accuracy falls 74% → 58% and duplicates rise 24% → 39% from 100 to 500 agents, with the same 40 target agents in every roster. Prompt size grows ~2.8× (cost per turn with it).                                                         |
| 6.2 | **Names alone can't route.** When the agent name doesn't mention the person in the prompt ("Ana's certificate" → _MacLeod Print Shop Ltd. COI…_), reuse accuracy is 17–28% at every size, vs 68–88% when it does. This is 3.1: the roster needs descriptions/people, not just names. |
| 6.3 | **At 500 agents the model stops fanning out.** "any update from Maya?" checks all four Maya agents at 250, but at 500 spawns an empty _Maya Update Check_ agent instead (ambiguous 86% → 14%).                                                                                       |
| 6.4 | **Same client, different job gets merged** in ~30% of cases at every size (e.g. Okafor renewal → Okafor COI agent), contaminating the COI agent's context. Not size-dependent: a naming/instruction problem, not only overload.                                                      |
| 6.5 | **Reminders route to the owning agent only 40–60% of the time**; otherwise a new reminder agent is created, so the trigger fires without the work's context.                                                                                                                         |

**Classifier** (`2026-10-27_121708_classifier_baseline`, 222 labeled emails, $0.05): high-importance recall 98%; low-importance false positives 15%; medium surfaced 58%; 8 of 12 phishing/injection emails surfaced as important, 6–7 of them with a clear scam warning in the summary; the other 4 were dropped silently (corrected 2026-10-29, section 9: an earlier version of this note said the surfaced ones had no warning, which the saved summaries don't support); missed a certificate holder correction again (cf. 4.7). Composio returns no importance field; the only signal is Gmail's own `IMPORTANT` entry in `labelIds`, which the classifier prompt includes. The first run (`…_classifier_label-leak`) put `IMPORTANT` on exactly the emails labeled high, leaking the answer key; with a Gmail-like noisy label instead, results barely moved (97% → 98% recall), so the classifier judges mainly by content.

**End-to-end scenario** (`2026-10-27_110213_scenario_old-labels`, first run, before the label fix; 3-run results in 7.3; 100-agent roster, full system, 600 ms simulated Composio latency, $0.16): 9/11 steps passed. Failures: Okafor renewal merged into the COI agent (6.4); "which clients still owe me documents?" timed out twice at 90 s and the user never got an answer (cf. 4.4). Also observed: a watcher email alone started the Okafor COI agent (4.1); drafts shown to the user twice; nothing sent or forwarded, and Marco's injected refund instruction was flagged to the user. Time to first reply ~3 s; time to the actual answer 10–36 s, 190 s for the cross-agent question.

**Comparing an improvement:** rerun with `--label <change>` and compare `summary.md` tables. Scoring changes can be re-applied to a saved run with `run_baseline.py rescore <results.json>` (no LLM calls). Run-to-run noise is about ±2 points on overall accuracy (7.1); combine repeated runs with `run_baseline.py compare`.

## 8. R&D: searching agents instead of listing them (2026-10-28)

Offline test (`run_baseline.py retrieval`, no LLM calls, ~15 s): for every routing case, rank the roster with `server/services/execution/agent_search.py` and check where the correct agent lands. Agent profile = name + first request + last requests + last result, built from the execution log. Local embeddings via `fastembed` (no API cost). Runs: `runs/2026-10-28_111319_retrieval_rnd-v1`, `…_retrieval_rnd-v1-all-{bge-small,bge-base,mxbai-embed-large}`.

| 500 agents, follow-up cases | Correct agent in top 10 | Top 1 | Name-opaque in top 10 |
|---|---|---|---|
| Names only, keyword (BM25) | 83% | 54% | 33% |
| Name + first request, keyword | 98% | 69% | 89% |
| Name + first request, embedding (bge-small / bge-base / mxbai-large) | 86% / 88% / 86% | 68% / 68% / 61% | 61% / 67% / 50% |
| Full profile, hybrid, keyword weighted 3:1 (bge-base) | 98% | 70% | — |

| # | Finding |
|---|---|
| 8.1 | **Profile content matters most.** Adding the agent's first request lifts top-10 recall from 83% to 98% at 500 agents, and name-opaque cases from 33% to 89%. |
| 8.2 | **Keyword search beats embeddings on this data**, whichever local model (small, base or large). The prompts are full of proper names and IDs, where dense embeddings blur ("Farah Tran" vs "Farah Tremblay"). Results hold for paraphrased prompts (97–98% top 10), so this is not exact-wording overlap with the generator. |
| 8.3 | **Embeddings help ranking, not recall.** A hybrid weighted 3:1 toward keyword search keeps 98% top-10 recall and raises top-1 from 65% to 70%. Equal weights lose recall (93–94%). |
| 8.4 | **The profile must include people.** The only top-10 misses at 500 are both the Okafor COI agent: its seeded history says "Okafor Landscaping" but never "Daniel", so "daniel's certificate" can't match. Real logs contain Gmail tool responses with sender names; the seeded histories don't. |
| 8.5 | **Dataset gaps for this design:** every seeded agent has one request (so "last 10 instructions" can't be tested yet), no tool responses (no sender names), no vague/semantic prompts ("the bakery thing"), and no confirmations or split messages ("okay", "yes send it"). |
| 8.6 | **Cross-agent questions are a separate problem.** "all my open claims" finds 47–75% of the relevant agents in the top 20; a candidate list of 10 can't answer it. Needs a different mechanism (e.g. search by job type). |
| 8.7 | **Search roster in the real Interaction Agent** (`OPENPOKE_AGENT_ROSTER=search`, `routing --agent-roster search`). Instead of every name, `<active_agents>` shows the top 10 search results for the message plus the 5 most recently active agents, each with purpose, latest status and last-active date, and the model gets a `find_relevant_agents` tool. One run each at 40 and 500 agents (`…_routing_search-v1/-v2/-v3`, ~$0.65 per run). |
| 8.8 | **v1 (search + descriptions):** duplicates on follow-ups 22% → 0% (40) and 37% → 1% (500); follow-ups reach the right agent 98% / 94% (baseline 75% / 57%); name-opaque follow-ups 89% / 83% (baseline 28% / 20%); prompt at 500 agents 16.1k → 7.1k tokens. But new jobs merged *more* (45% / 41% vs 33%): the descriptions show the client's other agent, and upstream's rule says to prefer existing agents. The model also answered from the cached "Latest" status instead of asking an agent; fixed with a rule that descriptions are only for picking an agent. |
| 8.9 | **Harness realism fix:** all seeded logs had today's timestamp, so a claim closed a year ago looked active. Seeded entries are now dated from the topic's start (shifted like the mailbox). No effect on baseline runs, which never show dates. |
| 8.10 | **v2 (+ "reuse only for the same job" rule):** merges at 40 agents 45% → 28%. A rule to treat agents "last active months ago" as finished was too aggressive (it skipped a real two-month-old billing agent) and was removed. New failure: when search found no agent, the model told the user the work didn't exist ("I don't see a Schmidt renewal"), although the emails are in the inbox. |
| 8.11 | **v3 (+ "no matching agent doesn't mean no such work"):** accuracy 94% at 40 and 86% at 500 (baseline 74% / 59%); follow-ups 96% / 94%; duplicates 1% / 0%; new jobs get their own agent 90% / 69% (baseline 67% / 67%); merges 10% / 24% (baseline 33% / 33%). Of the 19 failures at 500: 4 are the label problems in 7.10; 7 are prompts that become truly ambiguous at 500 because filler has another client with the same name and the same job (two Noras with billing issues, two Ana certificates, another Pereira renewal), where asking or picking that agent is defensible; 8 are real (3 merges, 1 guess, 1 "doesn't exist" answer, 3 cross-agent questions). Single runs; noise is about ±2 points overall but larger for small kinds. |
| 8.12 | **v4: conversation search for short replies.** v1–v3 searched the conversation only when the message had fewer than 2 meaningful words, which missed "yes send it", "go ahead" and "sounds good". Now every turn shows the top 10 for the message, the top 3 for the last 600 characters of the conversation, and the 5 most recently active agents (up to 18 cards; a message with nothing to search for gives its 10 slots to the conversation search). Offline: with a conversation about Linda's adjuster, Linda's agent is shown for "yes send it", "okay" and "go ahead" (before: only "okay"). Routing (`…_routing_search-v4-context`): 92% at 40 and 84% at 500, vs 94% / 86% for v3; 5 cases better, 9 worse, almost all cases that also flipped between earlier runs, so within noise. The test set has no confirmation cases, so the benefit isn't measured here. |
| 8.13 | **The `find_relevant_agents` tool adds cost, not accuracy, on this test set** (ablation `…_routing_search-v4-notool`, `OPENPOKE_AGENT_SEARCH_TOOL=0`, same code as v4 otherwise). In v3/v4 the model called the tool only for new-job requests (15–24 of 131 cases), as a "make sure no agent exists" check, and it never found a correct agent that the automatic list hadn't already shown. Without it: accuracy 92% / 87% at 40 / 500 (with it: 92% / 84%); new jobs get their own agent 79% / 72% (83% / 66%); 12 cases flipped, 7 better and 5 worse, all cases that also flip between earlier runs. Cost per run −14% ($0.29 vs $0.33) and typical response 0.3–0.4 s faster. The tool may still matter for vague requests and nicknames, which the test set doesn't cover. **Removed from the code** after this ablation: search mode now relies only on the agents shown each turn. |
| 8.14 | **Startup warm-up.** In search mode the server embeds every agent's profile in a background thread at startup (`AgentIndex.warm_up`, ~9 s at 500 agents). A search that arrives meanwhile doesn't wait for it: it uses keyword ranking for that one turn (0.04 s instead of blocking the server for ~9 s). Later changes are still caught by the profile-text cache. |
| 8.15 | **Confirmation on the final code** (search roster, no tool, warm-up). Routing (`…_routing_search-final-confirm`): 91% at 40 and 86% at 500 (v4 92/84, v4 without tool 92/87), so the gain holds within noise. End-to-end scenario (`…_scenario_search-final`, 100 agents, full system): 10/11 steps pass (baseline mean 8.7/11). The reminder now lands on Linda's claim agent (baseline 1 of 3 runs) and "which clients still owe me documents?" is answered by checking 8 existing quote agents (baseline 45–282 s, sometimes no answer). Still failing: the Okafor renewal merges into the COI agent. Nothing was sent (outbox: 3 drafts); one run only, so the unapproved-send issue (7.2) is not shown fixed. |

| # | Finding |
|---|---|

| 9.2 | **Fix:** one sentence in the classifier prompt (`server/services/gmail/importance_classifier.py`): an email that looks like phishing or fraud aimed at the user is important, and its summary starts with a warning not to act on it; don't mention phishing for ordinary emails. Summaries now open "WARNING: Do not act on this email." followed by the reason. |

## 10. Unit tests (2026-10-29)

`tests/` (pytest; `pip install -r server/requirements-dev.txt`, then `python -m pytest`): 57 tests plus 1 expected failure, offline, about 0.1 s. A stand-in embedder (hashed bag of words) replaces the local model, so nothing is downloaded and no LLM is called.

| File | Covers |
|---|---|
| `test_agent_search.py` | tokenizer, profiles (first + last 9 requests + latest result), BM25, the name-opaque case, the 3:1 hybrid against embeddings that disagree |
| `test_agent_index.py` | cards, the 10 + 3 + 5 candidates without repeats, "okay" giving its slots to the conversation search, recency, only changed profiles re-embedded, warm-up, searches never waiting for warm-up, keyword fallback when embeddings fail |
| `test_interaction_agent.py` | search-mode prompt rules, the upstream four tools in both modes, card escaping |
| `test_scoring.py` | the eval's routing outcomes and the scam-warning metric |
| `test_fake_gmail.py` | Gmail query matching in the fake backend (whole words: "vin" doesn't match "province") |

The known gap that "Will" is a stopword is kept visible as an expected failure (`xfail`). To check the tests catch real bugs, I broke the "okay" rule and the 3:1 weighting on purpose; the matching tests failed each time.
